# 坐标系与 TF 命名规范（集成方指南）

**文档性质：** 面向 lixel_sdk 集成方的坐标系概念说明与命名规范。解释 SDK 输出的位姿/点云在什么坐标系、ROS 桥接的 TF 结构、以及如何把设备接到自有载体（机器狗/车/无人机等）。
**关联文档：** 接口字段见 [api_reference_v2.md](api_reference_v2.md)。

---

## 1. 一句话结论

**SDK 输出的位姿与点云，坐标原点在设备的 IMU 点（设备基准），朝向遵循右手系（x 前 / y 左 / z 上）。** 设备不知道也不关心它被装在什么载体上——**把"设备 → 载体（狗心/车体中心）"的安装变换交给你（集成方）自己做**。这与行业主流 SLAM 设备的做法一致。

---

## 2. 基础概念

### 2.1 坐标系（frame）与刚体变换

一个坐标系（frame）= 一个原点 + 一组坐标轴朝向。两个 frame 之间的关系用一个**刚体变换**（旋转 R + 平移 t）描述。位姿（pose）本质上就是"某个 frame 相对另一个 frame 的刚体变换"。

**方向记号约定**：本项目用 `T_A_B` 表示"B 系在 A 系中的位姿"，即把 B 系下的点变换到 A 系的变换。例如 `R_W_I` = IMU 系相对世界系的旋转（世界←IMU）。

### 2.2 右手系与坐标轴朝向（ROS REP-103）

ROS 的坐标约定（REP-103）在业界被广泛采用，要点（内容依据 REP-103 概括）：

- **所有坐标系为右手系**（遵循右手定则）。
- 机体坐标轴：**x 向前、y 向左、z 向上**。
- 姿态旋转：绕 x = roll、绕 y = pitch、绕 z = yaw。
- 单位统一用 SI：长度 m、角度 rad、时间 s。

> 来源：ROS REP-103《Standard Units of Measure and Coordinate Conventions》。本项目位姿/IMU/点云均遵循此约定。内容为概括转述。

### 2.3 三个标准 frame：map / odom / base_link（ROS REP-105）

移动平台的坐标系语义（依据 REP-105 概括）：

| frame | 语义 | 连续性 |
|-------|------|--------|
| `map` | 世界固定的全局参考系（如地图原点） | **不连续**：重定位/回环时位姿可能发生离散跳变；但长期**无漂移** |
| `odom` | 世界固定的里程计系 | **连续无跳变**：位姿平滑演化；但长期**会累积漂移** |
| `base_link` | **刚性固连在平台基座上**的坐标系 | 平台本体，随平台运动 |

**父子关系约定**：`map → odom → base_link`。注意 `map` 与 `odom` 都"想"直接连 `base_link`，但 **TF 树中每个 frame 只能有一个父**，所以 REP-105 规定链式串接（导航系统发布 `map → odom`，里程计发布 `odom → base_link`）。

> 来源：ROS REP-105《Coordinate Frames for Mobile Platforms》。内容为概括转述。

**如何选 map vs odom**：需要"平滑、短期一致"（如局部避障、控制）用 `odom`；需要"全局、长期一致"（如回到地图上某点）用 `map`。

## 3. 本项目的坐标系与 TF 结构

### 3.1 SDK 输出的坐标系

SDK 订阅设备的 `device_locate`（位姿）与 `reloc_device_cloud`（reloc 点云），二者均为**设备（IMU）系**：

- **原点**：设备 IMU 芯片安装点（整机唯一基准）。
- **朝向**：右手系，x 前 / y 左 / z 上（REP-103）。
- 位置 = IMU 点在世界系下的坐标；姿态 = R_W_I（世界←IMU）；速度/角速度 = IMU 系。

> 设备端定位算法内部还有一套 Body/载体系（经外参偏移到"载体控制中心"），但**那套仅供设备内部导航，不经 SDK**。SDK 对外只给设备系，消除"到底是设备还是载体"的歧义。详见设备端 `coordinate_frames.md`。

### 3.2 ROS 桥接的 TF 结构（极简两层）

```
map ──(动态, ~100Hz, 来自 device_locate)──► base_link
 └ 世界/地图系                              └ 设备(IMU)基准
```

- `base_link` **直接等于设备 IMU 系**。桥接节点把 `device_locate` 位姿原样作为 `map → base_link`，**不做任何外参变换**。
- 世界系命名为 **`map`**：设备输出是 SLAM + 可重定位的全局位姿（绑地图、有重定位跳变），语义上是 `map`（REP-105）而非 `odom`。
- 话题：`/lixel/odom`（`nav_msgs/Odometry`，`frame=map`，`child=base_link`）+ `/lixel/tf`（`map → base_link`）。
- 点云 / IMU / 图像的 `frame_id` 均为 `base_link`（都是设备系数据）。

### 3.3 如何接到你的载体（关键）

设备只输出设备（IMU）系。要把它用在你的机器狗/车/无人机上，你需要**自己发布一层"设备 → 载体中心"的静态 TF**：

```
你的载体 TF 树：
map ──► base_link(设备IMU) ──► your_robot_center(狗心/车体中心)
                └ 你自己标定并发布这层静态 TF
```

用 ROS 静态 TF 广播即可（示例）：
```bash
# 参数：x y z qx qy qz qw parent child
ros2 run tf2_ros static_transform_publisher \
  <x> <y> <z> <qx> <qy> <qz> <qw> base_link your_robot_center
```
其中 `<x y z ...>` 是"设备 IMU 点 → 你的载体中心"的安装外参，由你在自己的载体上标定。

> **为什么这样设计**：设备是通用模组，可能装在任意载体上；把安装外参放在设备/SDK 里会绑死某一种载体。交给集成方，才能通用且无歧义。

## 4. 命名规范（本项目约定）

| 项 | 约定 |
|----|------|
| 世界系 frame | `map`（可通过 `map_frame` 参数改） |
| 设备基座 frame | `base_link`（= 设备 IMU 系，可通过 `base_frame` 参数改） |
| 坐标轴 | 右手系，x 前 / y 左 / z 上（REP-103） |
| 单位 | m / rad / s / m·s⁻¹ / rad·s⁻¹（SI） |
| 姿态表达 | 单位四元数（`w,x,y,z`），避免欧拉角万向锁 |
| TF 父子 | `map → base_link`（两层）；载体层由集成方在 `base_link` 下追加 |
| 载体变换归属 | **集成方负责**，SDK/设备不提供 |

## 5. 行业对标

主流 SLAM/定位设备同样遵循"设备输出传感器/设备系、载体变换交集成方"的原则：

| 来源 | 坐标系做法 |
|------|-----------|
| **ROS REP-103 / REP-105** | 右手系 x前/y左/z上；`map`(全局无漂移可跳变) / `odom`(连续会漂移) / `base_link`(固连基座)；父子链 `map→odom→base_link` |
| **Slamtec Aurora** | 位姿默认 SE3（`pose_se3_t` = 平移 + 四元数），并提供欧拉角版但文档警告万向锁；输出设备自身位姿，载体集成由使用方处理 |
| **Manifold Odin1** | ROS 驱动发布 `odom`/`map` 与 TF；里程计在 odom 系、SLAM 点云在 odom 系，需要 map 系时用 TF 转换 |
| **本项目 lixel_sdk** | 输出设备（IMU）系；ROS 桥接 `map → base_link`；载体变换由集成方叠加 |

> 上表信息来自公开文档/公开驱动仓库，未实测，为概括转述。

**共识**：设备厂商普遍**只保证"设备自身坐标系"这一层的正确性**，把"设备装在哪、载体中心在哪"留给集成方——因为厂商无法预知设备被装到什么平台上。本项目遵循同一原则。

## 6. 常见误区

1. **"SDK 给的位姿就是我机器人中心的位姿"** —— 错。是**设备 IMU 点**的位姿。要机器人中心，自己加一层 TF。
2. **把 `map` 当成连续无跳变** —— 错。重定位/回环时 `map` 系下位姿会**跳变**（REP-105）。需要平滑用 `odom` 语义。
3. **在 SDK/桥接里塞死某个载体的安装外参** —— 反模式。会绑死载体、换平台就错。
4. **欧拉角直接比较姿态** —— 有万向锁风险，用四元数。
